这份文档怎么读

我们的工程里现在有四份手写的代码文件,加起来不到 200 行。这份笔记把它们一行一行摆出来,左边是代码原文,右边是大白话翻译。

读的时候不需要背任何东西。看到眼熟就行。这份文档的使命是:三个月后你回来看自己的工程,随便指一行,都能想起"哦,这行是干嘛的"。

阅读顺序:先读第 0 课(十个概念,都是生活比喻),然后第 1~4 课慢慢看。遇到看不懂的词,先回到第 0 课查。

第 0 课 · 看懂代码需要的十个概念

全部用生活比喻,没有一句术语。

1. 代码就是一张"指令清单"

电脑是个极其死板、极其勤快的员工。代码就是你写给它的清单,从上往下,一条一条执行。它绝不会自己动脑筋,你写什么它做什么。

2. // 后面的话是给人看的,电脑直接无视

两个斜杠开头的叫"注释"。就像装修图纸上用铅笔写的备注——施工队(电脑)不看,只给你自己留的提示。我们的代码里写了很多注释,就是为了你回头看。

3. #include = "把那份文件的内容抄到这里来"

写代码经常要用到别人写好的东西。#include "某某.h" 的意思就是:把"某某"那份文件的全部内容,原样抄写到这一行来。类似写作文时"此处引用《某某文件》全文"。

4. 代码总是成对出现:.h 是说明书,.cpp 是施工队

我们的每个类都有两个文件:

  • .h 文件(头文件):一份说明书,写清楚"这个东西叫什么、由哪些零件组成、会做哪些动作"。只描述,不干活。
  • .cpp 文件:施工队,把说明书里承诺的每个动作,真正一步一步写出来。

为什么要分开?就像买房时你先看户型图(.h)决定买不买,不用关心墙怎么砌(.cpp)。别人用你的代码时只看 .h 就够了。

5. "类"是图纸,"对象"是按图纸造出来的实物

类(class)就是一张图纸:比如"汽车图纸"写着——有四个轮子、一个方向盘、会跑。图纸本身不能开。
按图纸造出来的每一辆真车,叫一个对象。我们写的 BaseCharacter 类是"战斗角色图纸";游戏里主角、每个小兵、Boss,都是按它造出来的一个个对象,各自有各自的血量。

6. "函数"是一个有名字的动作

函数就是给一串指令起个名字,方便反复使用。比如:

  • SetHealth(50) —— 名字:"设置血量";括号里的 50 是材料(用几来设置);这行命令执行完,血量就是 50。
  • 有的函数干完活会交回一个结果,比如 GetHealth() 会"汇报"当前血量是多少。括号里空着,意思是"不需要材料"。

7. "变量"是一个贴了标签的盒子

变量就是盒子,标签上写名字,里面装东西。比如 Health 这个盒子装着当前血量这个数字。数字会变(被打就减少),但盒子的名字不变。

8. "宏"是一条"查找替换"规则

看到 #define 开头的,那是宏。它的意思是:"以后凡是看到 A,都当作 B 处理"。和 Word 里的"查找替换"一模一样,只不过是在编译(把代码翻译成机器语言)之前自动替换。我们的代码用它偷懒:写一遍,顶四遍。

9. "指针"是门牌号,不是房子本身

看到 TObjectPtr<某物> 或者 某物*,那是"指针"。它不是那个东西本身,而是那个东西的门牌号——写着"它住在内存的哪个地址"。要真正找到那个东西,得按门牌号找过去(代码里用 -> 这个箭头,读作"去……家里")。

10. 虚幻引擎的"姓名牌"规矩

UE 给所有东西起名都带个前缀字母,看到就知道它是什么身份:

开头字母身份例子
U普通零件(不直接出现在游戏世界里)UMyAttributeSet 我们的属性表
A能放进游戏世界的"演员"(Actor)ABaseCharacter 我们的角色
F轻量的小数据结构FGameplayAttributeData 属性数据
I接口(一纸"必须遵守的约定")IAbilitySystemInterface
顺带说三个高频英文词(代码里到处是它们):Health = 生命值;Stamina = 体力/耐力;Damage = 伤害。Max 是 maximum(最大值)的缩写,MaxHealth 就是"血量上限"。

第 1 课 · 属性表的图纸 —— MyAttributeSet.h

这份文件回答一个问题:"角色的属性表,长什么样?"它只是说明书,不干活。文件位置:Source/ProjectUnreal/MyAttributeSet.h

第一部分:文件头(四句"抄过来")

代码原文大白话翻译
#pragma once对编译器说:"这份文件只准抄写一次"。防止别的文件抄它抄重了。几乎所有 .h 文件第一行都是它,是固定套路,不用深究。
#include "CoreMinimal.h"把 UE 的"基础工具包"抄过来。里面有最常用的基本功能(数字处理、文字处理等)。几乎每个 UE 代码文件都要它。
#include "AttributeSet.h"把"官方属性表图纸"抄过来。我们的图纸是在官方图纸基础上改装的,所以必须先拿到官方原版。
#include "AbilitySystemComponent.h"把"战斗大脑的图纸"抄过来。后面那个偷懒宏要用到它里面的东西。
#include "MyAttributeSet.generated.h"把引擎自动为我们生成的一份文件抄过来。我们从不自己写它,是 UE 在编译时偷偷生成的。铁律:它必须是最后一个 #include,放错位置直接编译失败(踩坑实录见故障手册)。

第二部分:一条偷懒用的"查找替换"规则

代码原文大白话翻译
#define ATTRIBUTE_ACCESSORS(ClassName, PropertyName) \定义一条替换规则,名字叫"属性访问器"。括号里是两个"空位":类名、属性名——以后用的时候往里填。行尾的反斜杠 \ 意思是"这行没写完,下一行接着算"。
GAMEPLAYATTRIBUTE_PROPERTY_GETTER(...) \ GAMEPLAYATTRIBUTE_VALUE_GETTER(...) \ GAMEPLAYATTRIBUTE_VALUE_SETTER(...) \ GAMEPLAYATTRIBUTE_VALUE_INITTER(...)规则的内容:一口气生成四个小工具函数,分别负责——拿到属性本身、读数值、写数值、设初始值。
为什么费这劲?因为 GAS 规定:属性不能直接读写,必须通过这四个"正规窗口"办理,否则属性的"变化广播"(血条刷新靠它)就收不到。每个属性都要这四个窗口,手写到吐血,所以用宏批量生产。

第三部分:图纸正文

代码原文大白话翻译
UCLASS()对引擎喊:"注意!下面要登记一个新类了!"引擎听到后,会给这个类办户口(让蓝图能看见它、垃圾回收会管它)。
class PROJECTUNREAL_API UMyAttributeSet : public UAttributeSet正式报名:
· class = 这是一张图纸
· UMyAttributeSet = 图纸名字("我的属性表",U 前缀见第 0 课第 10 条)
· PROJECTUNREAL_API = 盖个"本工程出品、对外开放"的章,别处的代码才允许使用它
· : public UAttributeSet = 在官方图纸(UAttributeSet)的基础上改装。官方图纸里已有的功能我们全部免费继承,只加自己的新东西。
GENERATED_BODY()UE 要求的"暗桩"。引擎办户口时要往类里塞一些它自己的东西,这个标记就是告诉它"塞这里"。固定套路,照抄即可。
public:"以下内容是对外公开的"——图纸的这部分谁都可以看、可以用。(相对的是 private,我们没用到。)
UMyAttributeSet();声明一个构造函数——"出厂设置单"。每造一个属性表对象,都会先照这张单子做一遍初始化。这里只挂个牌子(声明),具体干什么去 .cpp 里写(第 2 课)。

第四部分:五个属性(图纸的核心)

五个属性结构完全一样,讲透第一个,后面四个只是换名字:

代码原文大白话翻译
UPROPERTY(BlueprintReadOnly, Category = "Attributes")给下面这个变量办登记:
· BlueprintReadOnly = "蓝图可以读它,但不准改"(读和写分开授权,更安全)
· Category = "Attributes" = 在编辑器面板里归到"属性"这一组,好找
FGameplayAttributeData Health;图纸上的一个零件:
· 名字 Health = 生命值
· 类型 FGameplayAttributeData = "会广播自己变化的数字"。它不是普通数字——每当数值变化,它会自动敲锣通知所有关心它的人(比如血条 UI)。这就是 GAS 的属性必须用它的原因。
ATTRIBUTE_ACCESSORS(UMyAttributeSet, Health)动用前面那条偷懒规则:给 Health 批量造出四个窗口函数——GetHealthAttribute()(拿到属性本身)、GetHealth()(读血)、SetHealth(x)(写血)、InitHealth(x)(设出厂血量)。第 2 课你会看到它们被使用。

后面四组,一模一样的套路,只是换名字:

属性名中文干什么用
MaxHealth血量上限满血是多少。回血、扣血都不能超过它
Stamina当前体力攻击、翻滚都要消耗它(第 4、5 章用)
MaxStamina体力上限同上
Damage伤害(临时通道)最特殊的一个:它不是角色的状态,而是一个"快递单号"。别人打我们时,伤害数值先放在这个临时位子上,我们的代码(第 2 课)取出来扣血、然后立刻撕掉单子(清零)。它存在的唯一意义是把伤害数值从"攻击方"手里递到"受伤方"手里。

第五部分:两个"钩子"的预告

代码原文大白话翻译
virtual void PreAttributeChange(const FGameplayAttribute& Attribute, float& NewValue) override;钩子一:"任何属性马上要变化之前,先叫我一声"。
· virtual + override 意思是:官方图纸上本来有这个钩子(空壳),我们现在把它换成自己的版本
· 括号里的材料:Attribute = 是哪个属性要变;NewValue = 要变成多少
· 我们要在里面干什么?第 2 课揭晓(剧透:把数值夹在合法范围,血不能变负数)
virtual void PostGameplayEffectExecute(const FGameplayEffectModCallbackData& Data) override;钩子二:"每条规则(GE)结算完之后,叫我一声"。
· 材料 Data 是一个快递包裹:里面写着谁打的、改了哪个属性、改了多少
· 这是全游戏最重要的一个钩子:所有伤害、回血、耗体力,最终都在这里拆包处理。第 2 课细讲。
第 1 课小结:这份 .h 就是一张说明书,宣布了三件事:① 我有五个属性零件(血/血上限/体力/体力上限/伤害通道);② 每个零件配了四个正规办理窗口;③ 我在两个关键时刻安了钩子(属性要变时、规则结算后)。怎么干?看下一课。

第 2 课 · 属性表的施工 —— MyAttributeSet.cpp

上一课是"我承诺做什么",这一课是"我具体怎么做"。文件位置:Source/ProjectUnreal/MyAttributeSet.cpp

第一部分:文件头

代码原文大白话翻译
#include "MyAttributeSet.h"先把自己的说明书抄过来——施工队当然要知道图纸上承诺了什么。
#include "GameplayEffectExtension.h"把"快递包裹的拆包说明书"抄过来。上一课那个钩子二的材料 Data,它的内部构造写在这份文件里。不抄它,电脑就只知道"有个包裹"而不知道"包裹怎么拆",会报错(故障手册 P11 记的就是这个错)。

第二部分:出厂设置单(构造函数)

代码原文大白话翻译
UMyAttributeSet::UMyAttributeSet()"下面开始写 UMyAttributeSet 这张图纸的出厂设置单。"(:: 读作"……家的",即:UMyAttributeSet 家的 UMyAttributeSet 函数。函数和图纸同名,表示它是构造函数——每个新对象诞生时自动执行一次。)
InitHealth(100.f); InitMaxHealth(100.f); InitStamina(100.f); InitMaxStamina(100.f);四行,调用第 1 课用宏造出来的"设初始值"窗口:
出生血量 = 100,血量上限 = 100,体力 = 100,体力上限 = 100。
(100.f 里的 .f 只是告诉电脑"这是带小数的数",写 100 也行,写 100.f 更规范。)
注意:这只是"白板上写的默认值"。真正游戏里生效的数值来自策划配的 GE(笔记 01 的 GE_InitAttributes)——要改数值永远改 GE,不改这里。

第三部分:钩子一 —— 数值安检门(PreAttributeChange)

代码原文大白话翻译
void UMyAttributeSet::PreAttributeChange(const FGameplayAttribute& Attribute, float& NewValue)"下面写 UMyAttributeSet 家的钩子一"。材料:Attribute = 哪个属性要变;NewValue = 准备变成几。(& 的意思是"直接给你原件,不是复印件"——我们改了 NewValue,外面立刻生效,这正是安检门需要的能力。)
Super::PreAttributeChange(Attribute, NewValue);"先让官方图纸的版本也跑一遍。"(Super = 老爸,即官方图纸。)礼貌性动作:我们改装归改装,老爸该做的例行公事不能省。
if (Attribute == GetHealthAttribute())安检开始:"如果要变的这个属性是'生命值'……"(== 是"等于吗?"的提问;GetHealthAttribute() 就是第 1 课宏造出来的"属性本身",用来比对身份。)
NewValue = FMath::Clamp(NewValue, 0.f, GetMaxHealth());"那就把新数值强行夹在 0 到血量上限之间。"FMath::Clamp = 引擎提供的"夹子"工具:三个材料分别是(数值, 下限, 上限)。效果:血再扣不会变负数,再回不会超过满血。
else if (Attribute == GetStaminaAttribute()) { … }体力的同款安检,夹在 0 到体力上限之间。结构完全一样,不重复讲。

第四部分:钩子二 —— 拆包处理台(PostGameplayEffectExecute)⭐ 全课最重要

先回忆一下它在游戏里的位置:每次有一条规则(GE)对角色结算完毕,这个函数就被自动叫起来一次。伤害 GE 结算完 → 叫它;回血 GE 结算完 → 叫它。所有数值变动的"最后一站"。

代码原文大白话翻译
void UMyAttributeSet::PostGameplayEffectExecute(const FGameplayEffectModCallbackData& Data)"下面写 UMyAttributeSet 家的钩子二"。材料 Data 就是快递包裹:本次结算的完整信息。
Super::PostGameplayEffectExecute(Data);老规矩,先让老爸的版本跑一遍。
if (Data.EvaluatedData.Attribute == GetDamageAttribute())拆包检查:"这次结算改的是不是'伤害通道'(Damage)?"——我们暂时只关心这一种包裹,其他包裹(比如初始化 GE)直接放行。
读法:Data.EvaluatedData.Attribute 是"包裹.里面的结算单.上面的属性名",一层一层拆开看。
const float LocalDamage = GetDamage();"把伤害数值从通道里读出来,记在一个小本本上。"
· float = 这个小本本装带小数的数
· LocalDamage = 小本本的名字("本次伤害",Local 表示只在本次使用)
· const = 记上就不许涂改
SetDamage(0.f);"立刻把伤害通道清零。"这行极其重要:通道是公用的,这次用完不撕单子,下次新伤害进来就会和旧单子叠在一起,伤害翻倍出错。用完即撕,铁律。
if (LocalDamage > 0.f)"如果小本本上的伤害大于 0"(> 大于号,写成 > 是因为网页里要转义,代码里就是 >)。防御性检查:伤害是 0 就不用费事了。
SetHealth(FMath::Clamp(GetHealth() - LocalDamage, 0.f, GetMaxHealth()));真正扣血,一行干三件事,从最里面往外读:
① GetHealth() - LocalDamage:当前血量 − 伤害 = 新血量
② FMath::Clamp(…, 0, 上限):用夹子夹住,防止扣成负数
③ SetHealth(…):通过正规窗口写回去(血条 UI 立刻收到广播,准备刷新)
将来这里会加什么(第 4、5 章):查"无敌贴纸"(翻滚无敌帧)、查防御减伤、判断血量归零播死亡动画。全部都在这个 if 里扩展——这就是为什么 GAS 说"数值逻辑集中化":不管多少种伤害来源,最终都汇聚到这一个处理台。
第 2 课小结:出厂全设 100;属性变化前要过安检门(不能负、不能超);规则结算后要拆包裹(是伤害就:读出来 → 撕单子 → 扣血)。

第 3 课 · 角色的图纸 —— BaseCharacter.h

属性表只有数字,不会走路不会挨打。这份文件定义的是"一个会战斗的角色长什么样":它有身体(来自官方角色图纸)、有战斗大脑、有属性表。文件位置:Source/ProjectUnreal/BaseCharacter.h

第一部分:文件头与"剧透名单"

代码原文大白话翻译
#include "GameFramework/Character.h"把官方"角色图纸"抄过来。这张官方图纸非常强大:会走路、跳跃、碰撞、被玩家操控——我们全部免费继承。
#include "AbilitySystemInterface.h"把"战斗系统接口"抄过来。接口是什么?下一行就讲。
class UAbilitySystemComponent; class UMyAttributeSet; class UGameplayEffect;三行"剧透名单",学名叫前向声明。意思是:"下面会用到这三个名字,它们具体长什么样暂时不细说,你先知道有这三号东西就行。"
为什么不 #include 抄全文?因为 .h 会被很多文件抄写,抄得越轻,编译越快。等真正要用了,在 .cpp 里再抄全文(下一课会看到)。

第二部分:图纸正文 —— 这次有两个"爸爸"

代码原文大白话翻译
class PROJECTUNREAL_API ABaseCharacter : public ACharacter, public IAbilitySystemInterface报名:
· ABaseCharacter = 名字("基础角色",A 前缀表示能放进游戏世界,见第 0 课第 10 条)
· : public ACharacter = 第一个爸爸:官方角色图纸(送你会跑会跳的身体)
· , public IAbilitySystemInterface = 第二个爸爸:一纸约定。约定内容只有一条:"你必须提供一个窗口,让别人能找到你的战斗大脑。"签了这份约定,GAS 系统才承认你是"能战斗的角色"。
virtual UAbilitySystemComponent* GetAbilitySystemComponent() const override;这就是兑现那份约定的窗口:"来,这是我的战斗大脑的门牌号。"
· 返回值类型 UAbilitySystemComponent* = 战斗大脑的门牌号(指针,见第 0 课第 9 条)
· 名字超长?Get Ability System Component = "获取·战斗大脑·组件",UE 的风格就是把话说全
· const = 保证"只汇报,不偷改"
virtual void BeginPlay() override;声明一个引擎规定的固定节目:"这个角色进入游戏世界的那一刻,自动执行一次"。我们要在这个时刻给自己打"出生初始化"的规则(GE)。覆盖官方版本,内容去 .cpp 写。

第三部分:三个零件

代码原文大白话翻译
UPROPERTY(VisibleAnywhere, BlueprintReadOnly, Category = "GAS") TObjectPtr<UAbilitySystemComponent> AbilitySystemComponent;零件一:战斗大脑本身。
· VisibleAnywhere = 在编辑器面板里能看到它
· TObjectPtr<...> = 装着门牌号的盒子(第 0 课第 9 条),门牌指向战斗大脑
这个角色拥有的技能、身上的 Buff、属性表,全归这个大脑管。
UPROPERTY() TObjectPtr<const UMyAttributeSet> AttributeSet;零件二:属性表——就是第 1、2 课那张图纸造出来的实例,装着这个角色的血/体力数值。
· const = 只准通过它的正规窗口(第 1 课的四个函数)改数值,不准直接把表格换掉
UPROPERTY(EditDefaultsOnly, BlueprintReadOnly, Category = "GAS") TSubclassOf<UGameplayEffect> InitAttributesEffect;零件三:出生时要打的那条规则(GE_InitAttributes 的位子)。
· EditDefaultsOnly = 允许在编辑器的蓝图里填这个空(策划的活)
· TSubclassOf<UGameplayEffect> = 这个空里只能放"规则(GE)这一类的东西",放别的(比如一张贴图)编辑器会拒绝
注意:这里只留了空位,具体放哪条规则,是在蓝图 BP_BaseCharacter 里填的(编辑器四步配置的第 3 步)。
第 3 课小结:角色 = 官方送的身体 + 战斗大脑 + 属性表 + 一个"出生时打什么规则"的空位。外加两个承诺:能交出大脑的门牌号;出生时执行一次初始化。

第四部分:出生那一刻(BeginPlay)⭐

代码原文大白话翻译
void ABaseCharacter::BeginPlay()"下面写'进入游戏世界那一刻'要干的事。"
Super::BeginPlay();先让爸爸(官方角色)的版本跑——人家有一堆自己的开场准备要做,不能省。
if (AbilitySystemComponent && InitAttributesEffect)开场前先检查两件事,缺一不可:
① 战斗大脑在不在?(防万一)
② "出生规则"那个空位填了没有?(策划在蓝图里填了 GE_InitAttributes 才有)
&& = "并且",两个都成立才继续。
FGameplayEffectContextHandle Context = AbilitySystemComponent->MakeEffectContext();打规则第一步:造一个"操作记录单"。"大脑,给我开一张新单子。"(-> 还记得吗:"去……家里"——去大脑家里,叫它开单。)这张单子用来记录:这条规则是谁发起的、打在谁身上。
Context.AddSourceObject(this);"单子上登记发起人:我自己。"(this = 我,这个角色本人。)以后追查"这条规则是谁打的",有据可查。
const FGameplayEffectSpecHandle Spec = AbilitySystemComponent->MakeOutgoingSpec(InitAttributesEffect, 1.f, Context);打规则第二步:按规则配出一份"执行单"。"大脑,照着'出生规则'(GE_InitAttributes)配一份执行单:强度等级 1,关联刚才那张记录单。"
类比:规则(GE)是药方,执行单(Spec)是"按药方抓好的这副药"。
if (Spec.IsValid())"检查药抓好了没有。"(药方写错、药材不够,都可能抓不出来,先验货。)
AbilitySystemComponent->ApplyGameplayEffectSpecToSelf(*Spec.Data.Get());打规则第三步:"去大脑家里,把这副药给我自己服下。"——规则正式生效:血量、体力被设成 GE 里配的数值(100)。
Apply Gameplay Effect Spec To Self = 把·规则·执行单·应用到·自己。UE 函数名就是这句话的英文原文。结尾的 *Spec.Data.Get() 是"从门牌号取出执行单本体"的固定写法,眼熟即可。
这三步(开记录单 → 配执行单 → 服下)是"手动打一条规则"的标准流程,以后写代码打任何 GE 都长这样。不过大多数时候我们在蓝图里打 GE,一个节点就搞定,这段 C++ 只在角色出生时跑这一次。
第 4 课小结:出生时预装大脑和属性表;有人来要门牌号就交;进入世界那一刻,检查完毕后用三步标准流程把"出生规则"服下——角色满状态登场。

第 5 课 · 串起来:这些代码在游戏里什么时候被执行

代码不是一直跑的,是被一个个"时刻"触发的。完整时间线:

【双击打开工程】
  编辑器加载我们的 dll,四份代码处于"待命"状态,一行都没执行

【把 BP_BaseCharacter 拖进关卡,按 PIE 开始游戏】
  ① 角色诞生 → 执行【构造函数】(第 4 课第二部分)
       关心跳 → 预装战斗大脑 → 预装属性表
       (属性表自己的构造函数也跑了一遍:白板默认全 100,第 2 课第二部分)
  ② 角色进入世界 → 执行【BeginPlay】(第 4 课第四部分)
       检查 → 开记录单 → 配执行单 → 服下 GE_InitAttributes
       属性被改成 GE 里配的值
       改的过程中,每个属性都过了一遍【安检门】(第 2 课第三部分)

【将来:怪物一刀砍在主角身上(第 4 章实现)】
  ③ 攻击技能对主角打一条 GE_Damage(伤害 50)
  ④ 伤害数值先落在"伤害通道"上
  ⑤ 结算完毕 → 自动触发【拆包台】(第 2 课第四部分)
       认出是伤害包裹 → 读出 50 → 撕单子 → 100 − 50 = 50 写回血量
  ⑥ 血量变化广播 → 血条 UI 刷新(第 8 章)
你现在应该能理解这句话了:我们写的代码,本质是往引擎的几个"固定时刻"(诞生、入场、属性要变、规则结算完)里,挂上了自己定制的行为。引擎负责调度,我们负责在钩子里答题。这就是游戏开发的常态。
